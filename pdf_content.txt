Part III.
Under normal workload conditions during stress testing, users are expected to use
our AI link checker primarily for links that are new and have not been previously scanned by
other users. This is made possible by leveraging a centralized database and caching system for
previously scanned links, featuring a TTL (time-to-live) policy to ensure stale results are
periodically refreshed alongside an option for forced re-scanning when needed.
Another critical scenario involves multiple users attempting to scan uncached links
simultaneously. Because AI analysis takes several seconds per link depending on URL length,
these concurrent requests can heavily bottleneck our Python Flask backend. Without offloading
long-running tasks, the influx of HTTPS traffic risks overloading the server and causing
downtime, making the AI link checker unusable.
Lastly, our team identified a severe issue during a TTL burst scenario. Because our
app relies on forced re-scanning once a link's TTL expires, a mass cache expiration occurring
during peak usage hours forces simultaneous requests to trigger full AI scans. Because our
Python Flask backend is hosted on Render’s free tier with very low CPU resources, the

Part IV.
The response time for our AI link checker is dynamic, as processing latency scales
significantly depending on URL length, feature complexity, and the specific decision path
traversed within our Random Forest machine learning model. During stress testing, tracking
latency metrics—particularly the 95th and 99th percentiles—allows us to quantify performance
bottlenecks when concurrent requests process long, complex links during cache misses and
TTL expiration spikes on our resource-limited Render server infrastructure.
Another metric to track is Throughput (Requests per Second) under multiple
concurrent requests. In this scenario, we can identify the processing limits of Render’s free tier
and pinpoint the maximum acceptable request volume for our users. Again, this performance
will be dynamic, as it traces back to the dynamic analysis of our links—where key factors
include URL length, feature complexity, and the specific decision path traversed within our
Random Forest machine learning model.
Database and Cache Recovery Time. This metric measures the time required for our
central database and cache layer to return to normal response times (<5 ms) and healthy
CPU/IOPS utilization following a sudden traffic spike or TTL burst. Measuring database
recovery time is critical because prolonged latency or hanging connections following a traffic
spike directly impacts user retention and damages app reliability. If the database remains
sluggish long after a burst subsides, subsequent user requests will continue to stall or fail.
Furthermore, analyzing this recovery metric provides data-driven insights to improve our
backend resilience, connection pooling, and failover strategies in worst-case overload
scenarios.

Tool Selection & Justification
Grafana k6 was selected as the performance testing tool for evaluating the CSEC backend
system. The selection is justified by the following:
● Engine Efficiency (Go vs. Java/Python): Grafana k6 is built in Go. Unlike JMeter
(which consumes heavy system memory by launching a Java thread per virtual user) or
Locust (which uses Python's slower runtime), k6 uses lightweight goroutines. This allows
a single laptop to fire thousands of concurrent requests without lagging or bottlenecking
the client machine.
● Developer-Friendly Scripting (JavaScript/ES6): k6 scripts are written in plain
JavaScript/ES6, making test creation fast for developers working with mobile and web
technologies (like React Native) without needing to configure complex Java XML files in
a GUI.
● Code-Level Pass/Fail Thresholds: k6 allows defining explicit code rules directly inside
the test script (e.g., failing the build if 95% of responses exceed 1,500 ms). This aligns
directly with the project's goal of catching Render server thread starvation and HTTP 504
timeouts programmatically.
● Lightweight CLI and Automation: k6 runs as a single, lightweight command-line binary
that executes instantly and integrates directly into developer workflows and git
repositories without installing heavy dependencies.

Part VI.
The group will conduct stress testing using Grafana k6 to evaluate our Python Flask
backend hosted on Render. The testing methodology will follow standard performance testing
patterns, specifically:
1. Baseline Load Testing: Ramping up to a moderate concurrent user load to establish
normal response times (P95/P99 latency) for both cache hits and AI scan cache misses.
2. Step-Up Stress Testing: Incrementally increasing the volume of virtual users (VUs) to
identify the maximum request processing threshold (Requests Per Minute / RPS) before
server thread starvation and HTTP 504 timeouts occur on Render's free tier.
3. Spike & TTL Burst Testing: Introducing immediate, high-volume request bursts to
simulate mass cache invalidations, allowing us to measure error rates, client-side
fallback behavior, and database/cache recovery time post-surge.
The results from this stress test will help us identify vulnerabilities, improve backend
performance, and patch our application to ensure smooth operation. Additionally, it will help the
development team determine the right time to scale our infrastructure.
Part VII.
● Performance Degradation: At moderate loads, response times are supposed to be
Low and consistent because the server will be able to process cache hits as well as AI
scan without any problems. But with an Increase in the number of virtual users, Latency
is expected to increase, with AI scans, caches misses increasing at higher rate compare
to cached hits
● Possible Errors: With the increase in the number of requests to the maximum capacity,
there should be an increase in errors and the queuing of the request. HTTP 504 is
expected once the server can't keep up with increasing requests to the maximum
capacity.
● Failure Behavior: If the backend gets overloaded, it should simply stop serving requests
if it runs out of resources, otherwise, the app will probably fail or delay the scan result but
not crash. The spike test should also reveal the ability of the cache/database to cope
with a large number of misses.
● Recovery: As soon as traffic returns to its normal state, response times and mistakes
would be restored automatically, making a server restart unnecessary. The most
important point during the spike test would be the duration of cache and database
stabilization, which will indicate whether the system can handle a surge of traffic or
requires scaling.

Part VIII
● Group Analysis:
From our planned stress test scenarios, the scenario where we would see our system
fail would be a TTL burst coupled with high user load. This is because the Flask backend
is hosted in the free tier of Render with very minimal CPU capacity and the burst of TTL
will lead to many links being checked via the Random Forest algorithm all at once,
leading to exhaustion of worker threads on the server. The mode of failure which will
most affect the users will be request timeouts and slow scan results. The users depend
on the application to check their GCash account for phishing links. In case of failure, our
system should gracefully fail by queueing up the requests instead of failing totally. The
recovery will entail the system responding to requests within the normal period without
needing a manual server reboot as the recovery time would be indicated by the
database cache.Prior to deployment, the team needs to concentrate on enhancing the
backend’s performance when handling simultaneous AI scans for cache miss scenarios,
by either using task queuing or task offloading. Additionally, it would be wise to upgrade
the server capacity to accommodate TTL bursts.
